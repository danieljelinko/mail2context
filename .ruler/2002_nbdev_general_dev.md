# NBDev General Development Checklist

## Notebook-First Workflow
- [ ] Implement every feature inside nbdev notebooks; notebooks stay the source of truth.
- [ ] Use `000_nb_model.ipynb` as the structural template for new notebooks.
- [ ] Keep each code or test cell under ~15 lines; split longer logic into helper functions or new cells.
- [ ] Define helper functions and fixtures before the cells that use them.
- [ ] Mark public API cells with `#| export` so nbdev can generate modules correctly.

## Testing Discipline
- [ ] Import test helpers near the top of every notebook using this pattern:
  ```python
  try:
      from tag.core.utils.my_test import *  # Use tag-core if available
  except ImportError:
      from {{LIB_NAME}}.utils.my_test import *  # Fall back to local module
  ```
  Replace `{{LIB_NAME}}` with your project's library name (e.g., `docs2md`).
- [ ] Test each function in the very next cell with `test`, `test_eq`, `test_close`, `test_fail`, etc.
- [ ] Keep tests inline (no wrappers), concise (≤2 lines), and document intent with the `cname` argument instead of comments.
- [ ] Aim for single-line assertions; when the parameters are too long, extract helper functions so the test + expected value still fits on one line.
- [ ] Cover normal cases, edge cases (empty, None, boundaries), and failure paths using `test_fail`.
- [ ] Add an integration test cell per logical section plus a final end-to-end example that uses realistic data.
- [ ] Prefer `test_eq` (or enhance it) so it accepts an optional description/verbose flag instead of spreading commentary across multiple lines.
- [ ] For test comments pass it as cname argument, say "should do expected behaviour", example: "should replace '_' with '-'".

## Reuse & Structure
- [ ] Perform a quick DRY scan after finishing a notebook and extract repeated logic into shared utility `.py` modules.
- [ ] Re-export shared helpers so other notebooks can import them instead of duplicating code.
- [ ] Keep generated modules untouched—re-run the notebook instead of editing files that start with `# AUTOGENERATED!`.
- [ ] Apply behavior changes via `@patch` decorators (use `@patch(cls_method=True)` for classmethods or `@patch_to(ClassName, cls_method=True)` when attaching helpers externally) instead of assigning functions directly onto classes.

## Documentation & Examples
- [ ] Precede the final export cell with a usage example that shows how to call the main workflow.
- [ ] Prefer real datasets; if unavailable, create clearly-labeled mock data that mirrors production shape.
- [ ] Document any manual follow-up steps or data requirements in markdown cells so downstream agents can execute them.

## Delivery & Collaboration
- [ ] Start each notebook with a short plan outlining sections and expected exports.
- [ ] Provide numbered execution scripts (e.g., `01_run_ingest.py`) when the notebook needs to be automated.
- [ ] End with a “User validation” checklist describing how to rerun, what inputs to prepare, and how to verify outputs.
- [ ] When collaborating live, run notebooks through `executeCode (MCP)` and walk the user through the results.
