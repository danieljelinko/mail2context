# NBDev Development Rules

## Notebook-first

- Implement every feature inside nbdev notebooks; notebooks are the source of truth.
- Use `000_nb_model.ipynb` as the structural template for new notebooks.
- Keep each code or test cell under ~15 lines; split longer logic into helper functions or new cells.
- Define helper functions and fixtures before the cells that use them.
- Mark public API cells with `#| export`.
- Never edit files that start with `# AUTOGENERATED!` — re-run the notebook instead.

## Testing in notebook cells

> These conventions apply to nbdev notebook test cells only. For `.py` module testing, see `1002_tdd_red_green.md`.

- Test each function in the very next cell using `test`, `test_eq`, `test_close`, or `test_fail`.
- Keep tests inline (no wrappers), ≤2 lines. Use the `cname` argument for intent: `test_eq(f(x), y, cname="should replace '_' with '-'")`.
- Cover normal cases, edge cases (empty, None, boundaries), and failure paths.
- Add an integration test cell per logical section plus a final end-to-end cell using realistic data.

## Reuse

- After finishing a notebook, run a quick DRY scan and extract repeated logic into shared utility `.py` modules.
- Re-export shared helpers so other notebooks can import instead of duplicating.
- Apply behaviour changes via `@patch` decorators; use `@patch(cls_method=True)` for classmethods.

## Documentation

- Precede the final export cell with a usage example showing the main workflow.
- Prefer real datasets; if unavailable, create clearly-labelled mock data that mirrors production shape.
- Start each notebook with a short plan outlining sections and expected exports.
