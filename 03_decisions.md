# Decisions

| Date | Title | Context | Decision | Consequences |
|---|---|---|---|---|
| 2026-09-16 | D-001 IMAP for both mailboxes, with a Gmail-API fallback | Proton exposes mail **only** via Bridge IMAP/SMTP — there is no Proton API. Gmail offers both IMAP and a REST API. | Use IMAP/SMTP for both, so one code path serves both accounts. No Google Cloud project. | Uniform, scriptable, no OAuth. **Cost: IMAP has no thread concept** — threads must be rebuilt from `Message-ID`/`In-Reply-To`/`References`. **Fallback trigger: if header-based thread reconstruction proves unreliable in practice, swing the Gmail side back to the Google-Cloud/solvemail path**, which supplies `threadId` natively. Proton would still need header reconstruction regardless. |
| 2026-09-16 | D-002 Drop solvemail as a dependency, keep as reference | `solvemail` pulled in the entire Google API stack (`googleapiclient` 98 MB + `google` 7.2 MB + oauth libs) to serve a transport D-001 rejected. Reusable-to-us surface is ~40 lines of stdlib MIME code. | Removed from `pyproject.toml`. Feature analysis preserved in `260916__solvemail_feature_analysis.md`. Vendor `mk_email`/`_add_att`/`parse_raw` + the `_reply_headers` logic with attribution when needed. | Lean dep tree. If D-001's fallback ever fires, re-add: `git+https://github.com/AnswerDotAI/solvemail@bfe65f0e7b7c1b13dc30f7077c8a61953ac763eb` (v0.1.8, the version analysed). |
| 2026-09-16 | D-003 Drafts only — never send | The agent reads threads and composes replies; a misread thread that sends automatically has real blast radius. | Compose into the Drafts folder via IMAP `APPEND`. SMTP send stays unimplemented. | Owner reviews every outgoing message in their own mail client. Bridge's SMTP port 1025 stays unused for now. |
| 2026-09-16 | D-004 Plain Python by default, nbdev only for data exploration | Repo was scaffolded as uniformly nbdev (`nbs/`, `_modidx.py`). A CLI tool is a poor fit for notebook-first authoring. | Author modules as plain Python. Reserve nbdev notebooks for work needing human-supervised data exploration (e.g. tuning quote/signature stripping against real mail). | Mixed repo — `nbs/` presence still triggers ruler's nbdev rule tier, so those rules appear in `CLAUDE.md` but apply only to the notebook parts. |
| 2026-09-16 | D-005 Gmail has two access paths, kept deliberately | The claude.ai Gmail connector already works in-session with zero setup; the CLI needs its own credential. | Keep both: connector for interactive work in a Claude session, IMAP app password for the CLI, cron, and any non-Claude tooling. | Two auth mechanisms for one mailbox. Accepted — they serve different callers and neither blocks the other. |
| 2026-09-16 | D-006 Stay on IMAP — D-001's fallback is not needed | D-001 kept a Google-Cloud/solvemail escape hatch in case header-based thread reconstruction failed in practice. | Validated against 400 real Proton messages: 262 threads, 105 multi-message, 0 missing `Message-ID`, 0 threads mis-ordered in UTC. A 14-message thread spanning 5 subject lines grouped correctly. **Staying on IMAP for both accounts.** | The escape hatch stays documented in D-001 but is now dormant. Re-evaluate only if Gmail's mail behaves differently from Proton's — its threading is not yet validated. |
| 2026-09-16 | D-007 Verify by invariant + audit, not by eyeballing | Threads are rebuilt locally and HTML is flattened to text; both can lose content silently, and Bridge offers no ground truth to diff against. Owner requires zero loss. | Three defences: (1) `just audit` compares every long text run in source HTML against rendered output whitespace-insensitively, plus link targets, image alts and attachment names, exiting non-zero on loss; (2) test-suite invariants that every message lands in exactly one thread and the partition is order-independent; (3) `just export` / `just thread-raw` for manual comparison against the mail UI. | Loss is measurable and CI-gatable rather than a matter of opinion. The audit found 489 dropped URLs, 42 unnamed attachments and 105 destroyed image alts that reading the output would not have revealed. Quote stripping is deliberately **out** of the audit's scope — it removes ~41% of characters on purpose. |
| 2026-09-16 | D-008 Always ask recipients and threading before drafting | A reply defaults to the thread's last sender and inherits the old subject. On multi-party work threads both defaults are frequently wrong, and both fail silently — a thank-you can land under `Re: invitation ... ceremonie des diplomes`, addressed to one of five people. | The mail skill must ask the owner two questions every time, even for a draft: who receives it (last sender / everyone / a named subset), and whether it continues the thread or starts a new conversation. Show the `draft-preview` To/Cc/subject/OMITTED block before creating anything. | Slower by one exchange; removes a class of mistake that is invisible until after sending. `just draft-args` gives full control (`--to`, `--all`). |
| 2026-09-16 | D-009 Keep building threading headers despite Proton dropping them | Proton strips `In-Reply-To` on draft APPEND, so the work appears wasted for that account. | Keep the RFC 5322 threading logic. It is correct, it is what Gmail and every other IMAP server expect, and the cost is nil. Document the Proton behaviour rather than removing the headers. | Proton drafts do not thread; the owner is told so at draft time. If true threading matters for a Proton reply, compose it in the Proton UI from the rendered thread. Revisit when Gmail is configured — if Gmail preserves the headers, the split is provider-specific, not a design flaw. |
| 2026-09-16 | D-010 Deterministic Markdown→HTML, never LLM-generated markup | Draft HTML was being written by the agent each time: costs tokens, varies run to run, and cannot be reviewed once. | `mail2context/markdown_mail.py` renders Markdown to email-safe HTML with markdown-it-py plus inlined styles, exposed as `just md2html` / `just md-preview` and used automatically by `draft`/`compose`. | Reproducible and free. Styling changes are one edit in `_STYLES` rather than a prompt. The agent writes prose only. `--plain` escapes Markdown when asterisks are literal. |
| 2026-09-16 | D-011 **TEMPORARY** send capability, allowlisted to two addresses | Round-trip testing cannot verify header survival, real quote blocks or rendering without mail actually travelling. D-003 forbids sending entirely. | Owner authorises sending **only** to `dj@ai4hu.org` and `daniel.jelinko@gmail.com`, enforced by a hard allowlist in code with a test asserting any other recipient is refused. **This is temporary.** Once the round-trip suite passes, the send capability is REMOVED and D-003 (drafts only) resumes in full. | Phases 2-4 of `01_plan.md` can run. The allowlist is never widened — a new address means a new decision, not an edit. Removal is `01_plan.md` Phase 6 and is not optional; leaving send enabled after validation violates this decision. |
| 2026-09-16 | D-012 The audit measures the HTML→text conversion, not "whatever `extract_text` returned" | `just audit gmail 900` reported 26,967 lost items where Proton reported 0. Root cause: `audit_messages` diffed the message's **HTML** part against `extract_text()`, which returns the **plain** part when one exists. Proton has no multipart/alternative mail at all, so the mismatch could not occur there; 173 of 200 Gmail messages have both parts. | The audit now renders the HTML part with `html_to_text()` and compares against that — the conversion D-007 actually claims to measure. `_html_to_text` is promoted to public `html_to_text` as the audited unit. | Gmail and Proton both report **0 losses across 900 messages**. The Proton figure is unchanged, so the audit was not weakened: on HTML-only mail the two comparisons are identical. `extract_text`'s preference for the plain part is untouched — that is a rendering choice, not a loss. |
| 2026-09-16 | D-013 Any BeautifulSoup rewrite pass must run innermost-first | Two separate href/alt losses had the same shape: `find_all(tag)` returns a static list, and replacing an outer node detaches an inner one whose own replacement then writes into a detached subtree. Cost 214 lost hrefs per 300 Gmail messages (nested anchors) plus a class of lost tracking links (anchors parsed inside an `<img>`). | `_inline_links` sorts anchors by depth, deepest first. `_inline_images` inserts the alt text then `unwrap()`s an image that has children rather than replacing it outright. | Both are regression-tested against the real-world markup that produced them. The older "rewrite images before anchors" rule still holds; this generalises it. Adding any new rewrite pass over the soup means honouring the same ordering. |
| 2026-09-16 | D-014 D-009 is Proton-specific — Gmail drafts thread correctly | D-009 kept the RFC 5322 threading headers despite Proton stripping them on APPEND, and left open whether the behaviour was universal. A root+reply pair appended to `[Gmail]/Drafts` returned with `In-Reply-To`, `References` **and** the original `Message-ID` intact, grouping as one thread of 2. | Keep the threading logic, and scope the warning: a **Proton** reply draft will not thread in the owner's UI; a **Gmail** one will. | The mail skill's blanket "Proton drafts do not thread — Gmail is untested" line is now answerable. Verified with a self-addressed throwaway pair, binned afterwards; no third party involved. |
| 2026-09-16 | D-015 D-009 is about draft APPEND, not about Proton mail | D-009 and D-014 established that Proton strips `In-Reply-To` and rewrites `References` on **draft APPEND** while Gmail preserves them. Whether a real **send** behaved the same way was untested, and the difference decides whether replies composed here thread for their recipients. | Verified over a live 6-message Proton↔Gmail conversation (run `91fcac`): **both providers preserve the client-supplied `Message-ID`, `In-Reply-To` and the full `References` chain on sent and received mail.** Proton *appends* its own `@protonmail.internalid` to `References` rather than replacing it — the rewrite is additive here, destructive only on draft APPEND. | The "this will not thread" warning is now scoped to **Proton drafts**, not to Proton replies in general: mail actually sent threads correctly on both sides. `check_reply_chain` asserts `References` **contains** the expected ancestors rather than equalling them, so Proton's extra id is tolerated by design; any future equality check on `References` would fail on Proton for this reason. |
| 2026-09-16 | D-016 Attachment contents are a separate feature, not part of content fidelity | Phase 3 asks that attachment filenames surface and bytes match. Only filenames are surfaced to the LLM; contents are never read. Folding extraction into Phase 3 would mix a new capability (format handling, output location, size limits) into a verification phase. | Phase 3 proves bytes match by sha256 inside `check_attachment` (stdlib payload decode, no production change). Surfacing contents is its own plan entry after Phase 6. | Phase 3 stays a fidelity phase and needs no new production code beyond the table fix. Attachment extraction can be designed without the send capability, so it is not blocked by Phase 6. |
| 2026-09-17 | D-017 Enforcement lives outside the repo: `mail-guard`, three levels, separate repo | Any guard inside mail2context (allowlist, skill text, CLI) is editable by the agent and bypassable by a fresh `smtplib` script. The owner wants a guarantee that survives the agent, switchable by hand, in three levels: read+draft only; +move/delete; everything. Move/delete share the IMAP port and password with read and draft, and no OAuth scope or Bridge setting separates them. | Build `~/Work/tools/mail-guard` as its own repo: root-owned nftables rules per uid for SMTP (levels 2/3), a filtering IMAP proxy running as its own system user holding the real credentials (level 1), a root-owned level file and `sudo mail-guard 1\|2\|3`. APPEND only to Drafts at every level. mail2context must work with the guard on (plaintext loopback proxy) and off (direct, as today). | The agent has no passwordless sudo, which is the property the design rests on. The claude.ai Gmail connector is outside the guard and must be scoped separately. Phase 6's "delete the send code" may be replaced by "send only through the guard at level 3" once the scheduled-send study (01_plan.md) is decided. |
| 2026-09-17 | D-018 Level 1 allows `STORE +FLAGS` of `\Answered` and `\Flagged` only | Level 1 as drawn refused all STORE, but Phase 4 needs `\Answered` set after a reply, and `\Flagged` is triage. Opening level 2 for that would also open move and delete. | The guard forwards `[UID] STORE <set> +FLAGS[.SILENT] (<subset of \Answered \Flagged>)` at level 1. `-FLAGS`, bare `FLAGS`, `\Seen` and `\Deleted` still need level 2. | Phase 4 runs at level 1. The tool still cannot mark anything read or deleted there. Tested both ways in `mail-guard/tests/test_filter.py`. |
| 2026-09-17 | D-019 Scheduled send is the provider web UI's own feature on a tool-made draft | Neither Gmail's API nor Proton offers schedule-send; a local scheduler would keep a send capability alive at fire time. The owner weighed both (Track S). | Option (a): the agent drafts, the owner opens the draft in Proton's or Gmail's web UI and uses *Schedule send*. No code. | D-003 intact; nothing on this machine sends on a timer. Proton IMAP drafts still do not thread in Proton's UI (D-009), which the owner sees before scheduling. |
| 2026-09-17 | D-020 Level 3 sends through the guard's SMTP relay; real passwords leave `.env` | With the Gmail app password readable by uid 1000, the agent could send from any host it can ssh to; nftables only guards this machine. The owner also keeps the `docker` group (root without a password) and will disconnect the claude.ai Gmail connector. | The guard holds the real IMAP and SMTP credentials root-owned; mail2context presents per-account tokens (`*_PASS` in guard mode) that work only on loopback; uid 1000 is rejected on every mail port at every level; the level is a file, never an nft change. | Owner rotates the Gmail app password once after install. Docker group membership is a documented gap the guard does not cover. `.env` in guard mode holds tokens, ports and `*_TLS=none`. |
| 2026-09-17 | D-021 Phase 6 confines the send code instead of deleting it | D-011 promised deletion after validation because code was the only guard. With `mail-guard`, `send.py` reaches the wire only through the relay at level 3, which the owner opens with sudo for a bounded time. | Keep `send.py`, the round-trip recipes and the D-011 allowlist (as a second belt); replace the TEMPORARY markers by references to this row once the guard is live. Sending remains something only the owner enables. | D-011's allowlist is no longer the guarantee, the level is. A new recipient still means a decision, not an edit, while Phases 4-5 run. |
| 2026-10-29 | D-022 The tool may delete one draft by UID, from Drafts only | A stale agent-made Proton draft had to be deleted by hand in the web UI. D-003 limited writes to APPEND; deleting widens what the tool mutates, and a delete through IMAP is permanent on both providers (see `04_learnings.md`). | `just draft-delete UID` removes exactly one message: from the mailbox the server flags `\Drafts` (no folder argument exists), carrying the `\Draft` flag, by `UID STORE +FLAGS.SILENT (\Deleted)` then `UID EXPUNGE <uid>`, refused without UIDPLUS. It shows the `draft-list` row and asks, `--yes` for scripts, `--dry-run` to look. An agent runs it only when the owner asks, after showing that row. | D-003 still holds: nothing sends. Nothing outside Drafts can be deleted, and no bare `EXPUNGE` is ever issued. Under mail-guard it needs level 2 (STORE `\Deleted` is not in D-018's level-1 exception); the refusal names the command to raise it. |
| 2026-10-31 | D-023 Headers-only read for indexers | com-index needs whole mailboxes; `BODY.PEEK[]` takes minutes per few hundred on Gmail, and nothing exposed UIDVALIDITY. com-tools D-017. | `fetch_headers` (EXAMINE, named fields, batched, past a UID, optional date) and `read_folder_state` (STATUS). | Same read-only guarantees as `fetch_recent`. About 500 messages per second on Gmail. |
