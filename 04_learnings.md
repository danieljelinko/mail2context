# Learnings

| Date | Title | Non-obvious truth | Implication |
|---|---|---|---|
| 2026-09-16 | `protonmail-bridge` launches a GUI | The `/usr/bin/protonmail-bridge` wrapper starts the Qt GUI — even `--help` and `--version` do, then block. The headless core is `/usr/lib/protonmail/bridge/bridge`, which supports `--cli`, `--noninteractive`, `--grpc`. | Always invoke the `/usr/lib` path from scripts or an agent. Wrap any exploratory call in `timeout`. |
| 2026-09-16 | Bridge opens 1143/1025 before any account exists | Bridge binds IMAP 127.0.0.1:1143 and SMTP 127.0.0.1:1025 as soon as it starts — *before* login. | A listening port is **not** evidence of a working mailbox. Health-check by logging in over IMAP, not by `ss`. |
| 2026-09-16 | Bridge needs a paid Proton plan | Bridge is not available on Proton free tier. | If IMAP login fails after a successful Bridge login, check the plan before debugging the client. |
| 2026-09-16 | Bridge vault key vs. gnome-keyring | First run logged `no vault key found, generating new — credentials not found in native keychain` and wrote `~/.config/protonmail/bridge-v3/vault.enc` + `keychain.json`. | Benign once. If it recurs on **every** restart, Bridge isn't persisting to the keyring and the account must be re-added each time — check `keychain_state.json`. |
| 2026-09-16 | Bridge self-update needs a restart to take effect | Bridge announced "a new version (3.26.0) was installed", but the running IMAP server still greets as `Proton Mail Bridge 03.24.02`. The download is staged, not live. | Read the running version from the IMAP greeting, not from the install message and not from `dpkg -l`. Restart Bridge to actually land an update. |
| 2026-09-16 | solvemail's MIME extractors are not MIME extractors | `txt_part`/`html_part`/`att_parts`/`walk_parts` parse **Gmail REST payload dicts** (`{'mimeType':..,'body':{'data':..}}`), not `email.message.EmailMessage`. Only `mk_email`/`_add_att`/`parse_raw` are stdlib-pure. | Over IMAP these cannot be reused verbatim. Use `msg.get_body(('plain','html'))` / `msg.iter_attachments()` instead — ~10 lines. |
| 2026-09-16 | Proton Bridge IMAP offers no THREAD or SORT | Bridge advertises only `AUTH=PLAIN ID IDLE IMAP4rev1 MOVE STARTTLS UIDPLUS UNSELECT`. Server-side threading and sorting are absent. | Thread reconstruction from `Message-ID`/`In-Reply-To`/`References` is mandatory for Proton, not a preference (confirms D-001's risk). Upside: `UIDPLUS` returns the new UID on draft `APPEND`, and `IDLE` gives push instead of polling. |
| 2026-09-16 | Bridge IMAP needs certificate verification disabled | Bridge serves STARTTLS on 1143 with a self-signed cert. A default `ssl` context rejects it; connecting requires `check_hostname=False` + `CERT_NONE`. | Not a misconfiguration to debug. Safe here only because the endpoint is `127.0.0.1` — never copy this setting to a remote IMAP host. |
| 2026-09-16 | The venv was moved, so its console scripts were dead | `.venv/` was copied from the repo's former path; every `bin/` shebang still read `/home/helinko/Work/guess-class/mail2context/.venv/bin/python3`. `uv run python -c ...` worked (uv picks the interpreter) while `uv run pytest` failed with "Failed to spawn". | A moved venv is not relocatable. `rm -rf .venv && uv sync --all-groups` is the fix. Suspect this whenever a module import works but its CLI entry point does not. |
| 2026-09-16 | `imaplib` does not quote mailbox names | `M.select('All Mail')` fails with `BAD [Error offset=17]: expected CR` — the space ends the command. It must be passed as `'"All Mail"'`. | Quote every mailbox name reaching `imaplib`. Proton exposes `All Mail` and every label as `Labels/<name>`, so spaces are the norm here, not the exception. |
| 2026-09-16 | Proton sends UTC, correspondents send local | The mailbox mixes `+0000` (Proton's own) and `+0200` (French correspondents). Truncating a `Date` header for display hides the offset and makes correctly-sorted threads look scrambled. | Always compare normalised UTC, never the header string. When a thread looks mis-ordered, print the offset before believing it. |
| 2026-09-16 | Most Proton mail has no plain-text part | 85 of 120 sampled messages are HTML-only; only 35 carry `text/plain`. | HTML→text is the **primary** extraction path, not a fallback. A renderer that treats `text/plain` as normal will return nothing for 70% of the mailbox. |
| 2026-09-16 | CSS selectors alone cannot strip quotes | Proton/Gmail wrap quoted originals in `.protonmail_quote`/`.gmail_quote`, but Zimbra and Outlook emit a bare `De:`/`Envoyé:` header block with no class to select. Those are the business correspondents (agroparistech, live.fr, lacsf67.org). | Selector stripping must be paired with a text-level cut at the attribution line. Together: 16/400 messages retained quotes → 1/400, and 30% → 41% of characters removed. |
| 2026-09-16 | Bridge exposes no conversation id | Proton headers include `X-Pm-Internal-Id`, `X-Pm-External-Id`, `X-Pm-Gluon-Id` — all per-message. Nothing identifies a conversation. | There is **no server-side ground truth** to validate thread reconstruction against. Correctness has to come from invariants (`just check`) and manual comparison, not from diffing against Proton. |
| 2026-09-16 | Sorting RFC 2822 Date strings sorts by weekday | `Date` starts with the weekday name, so a string sort orders Fri < Mon < Sat < Thu < Tue < Wed. The thread list looked plausible while being wrong. | Always sort on `thread.sent_at(m)`, never the raw header. Regression test: `test_sent_at_orders_dates_that_string_comparison_would_scramble`. |
| 2026-09-16 | Rewrite images before anchors, never after | Newsletters wrap banners as `<a href><img alt="…"></a>`. Replacing the anchor first destroys the nested `img`, losing its alt — 105 alts in a 200-message sample. | Order matters in `_html_to_text`: `_inline_images` then `_inline_links`. An anchor's `get_text()` is empty for a linked image, so the alt must already be text by then. |
| 2026-09-16 | Grouping only search hits rebuilds partial threads | `--from barbara` returned the FIPDES thread as 6 messages keyed `5f2f67c1`; `just threads` shows the same thread as 14 messages keyed `e95f7a81`. Reconstruction depends on which messages you fetched, so a filtered fetch yields a different thread *and* a different key. | Search must union its hits with the recent window before grouping. Any code path that groups a filtered subset will silently produce partial threads and keys that do not agree with the rest of the tool. |
| 2026-09-16 | Proton reports `\\Recent` on everything and duplicates forwarded flags | A 20-message INBOX fetch returned `\\Recent` on all 20, plus both `$Forwarded` and `Forwarded`. | Do not treat `\\Recent` as "new". Read unread as the *absence* of `\\Seen`, and only when flags were actually fetched — `is_unread` returns False when no flags are present, so a flagless fetch cannot masquerade as all-unread. |
| 2026-09-16 | `just --list` signatures are not copy-pasteable | just arguments are **positional**; the `name="value"` in a listed signature is a default. Pasting `just draft key body account="proton"` passes the literal string `account=proton` as the next positional. | The CLI now detects `name=value` literals and explains. Never document a just recipe by quoting its signature — show a real invocation. |
| 2026-09-16 | Replying to a thread's last sender silently drops the rest | A four-person Zimbra thread's last message was from Élodie, so the reply addressed only her — Barbara, Lucile and Isabelle vanished with no indication. Autoresponders also stack `Auto:` onto the subject, surviving a plain `Re:` strip. | `build_reply` strips `Re:/Fwd:/Auto:` noise, and the CLI prints an `OMITTED` line naming everyone left out. Verify that line before any draft; `--all` copies them in. |
| 2026-09-16 | Replying to your own last message addresses yourself | When the owner sent the last message in a thread (chasing an unanswered mail — the common case), reply-to-last-sender resolves to the owner. The preview read `draft to: dj@ai4hu.org`. | `build_reply` falls back to that message's `To` when the last sender is the author, which is what a mail client does. Always read the preview's To line before drafting. |
| 2026-09-16 | Proton discards threading headers on draft APPEND | A reply built with correct `In-Reply-To`/`References` arrives in Drafts with `In-Reply-To` **absent** and `References` replaced by a `@protonmail.internalid` value; `Message-Id` is rewritten too. Verified on a real draft — the preview printed the right headers, the stored draft had none. | A Proton draft made this way will **not** thread to its conversation in the Proton UI. Recipients' clients usually still group it by subject. Unit tests cannot catch this: the message is correct until Proton rewrites it. To keep true threading, reply from the Proton UI using the rendered context instead. Gmail is untested and may behave differently. |
| 2026-09-16 | A plain-text draft renders monospace in Proton | A `text/plain`-only draft is shown in a fixed-width font by Proton's composer, so a French business letter reads like a terminal dump. | Always attach a `text/html` alternative. `build_reply`/`build_message` now do, via `_set_body`. |
| 2026-09-16 | Never hard-wrap an email body | The first live draft was wrapped at ~76 chars, so the composer showed sentences broken mid-phrase (`...frais liés à` / `ma mission du 2 au 5 septembre.`). Those breaks are frozen into the message and do not reflow. | Write one line per paragraph and let the client wrap; use single newlines only where a break is meant, such as a signature. The HTML part maps blank lines to `<p>` and single newlines to `<br>`, so deliberate breaks survive and accidental ones would not have. |
| 2026-09-16 | Header-level verification is not verification | Checking To/Subject/In-Reply-To/body-present declared the first draft a success. Opening it showed monospace rendering and mid-sentence wrapping — both invisible at header level. | For anything a human will read, inspect the rendered result, not just its structure. Ask the owner for a screenshot when the renderer is not ours to run. |
| 2026-09-16 | The real signature is styled markup, not text | Sent mail shows `AI` + `<span style="color: rgb(59, 131, 194)">4</span>` + `HU \| Artificial Intelligence for humans`, each span carrying its own `Helvetica` family, inside a `protonmail_signature_block-user` div. Proton does **not** add the configured signature to a draft appended over IMAP. | The signature must be supplied by us or the mail goes out unbranded. Kept verbatim in `signature.html` so the blue 4 survives; `signature.txt` serves the plain part. |
| 2026-09-16 | Markdown joins soft-wrapped lines, which eats signatures | With markdown-it's default `breaks: False`, `Dani JELINKO\nAI4HU \| ...` renders as one line. | `breaks: True` for mail: a newline in an email body is intentional. The no-hard-wrap rule still stands, and now matters more, since wraps become visible `<br>`. |
| 2026-09-16 | `just bridge-status` could not report DOWN | It grepped `ss` for the unanchored string `127.0.0.1:1143`, which matches Ollama's `127.0.0.1:11434`. With Ollama running — the normal state on this machine — it printed "up on 1143" while Bridge was stopped. | The mail skill's first instruction was a check that always passed. `bridge-status` now logs in over IMAP (`check_account`) instead of inspecting ports, and exits non-zero when down. Never health-check a service by grepping for a port substring. |
| 2026-09-16 | Bridge binds 1143 before it can serve the account | After `systemctl --user restart protonmail-bridge`, port 1143 accepts connections within 2s, but IMAP LOGIN returns `no such user` for another ~5s while the vault loads. | Extends the older "a listening port is not evidence" row with a number: after any Bridge restart, poll `just bridge-status` until it exits 0 rather than trusting the port or a fixed sleep. |
| 2026-09-16 | The loss audit compared two different renditions of a message | `audit_messages` always diffed the **HTML** part against `extract_text()`, but `extract_text` returns the **plain** part whenever one exists. On multipart/alternative the HTML rendition legitimately carries tracking URLs, image alts and styled boilerplate the plain one never had, so all of it read as loss: 26,967 phantom items over 900 Gmail messages. | Proton mail contains **no** multipart/alternative messages at all (0 of 200 sampled), so the defect was structurally invisible until Gmail was scanned — 173 of 200 Gmail messages have both parts. The audit now measures `html_to_text(html)` against that same HTML, which is what D-007 says it measures. A verification tool that only ever saw one corpus was never verified. |
| 2026-09-16 | An anchor nested in another anchor loses its href | `_inline_links` iterated `soup.find_all('a')` in document order; replacing an outer anchor detaches the inner one, so the inner `replace_with` writes into a detached subtree. html.parser **does** keep `<a>` inside `<a>`, and bulk senders wrap a tracked wrapper around a tracked button constantly: 214 hrefs lost in 300 Gmail messages. | Anchors are now rewritten deepest-first. Same hazard as the older "rewrite images before anchors" row — with BeautifulSoup, any `find_all` + `replace_with` pass over a tree that can nest must run innermost-first. |
| 2026-09-16 | Mixing bare and self-closed `<img>` makes html.parser nest into the image | A document containing a bare `<img src=…>` makes a later self-closed `<img …/>` parse as an **open container**, so the anchor after it becomes the image's child. `_inline_images` replaced the image outright and took that anchor's href with it. Neither tag is malformed alone — it is the mix that triggers it. | `_inline_images` now inserts the alt text and `unwrap()`s an image that has children instead of replacing it. Reproduced minimally as `<img alt="brand"><img alt="" …/><a href=…>`; confirmed against the real 59 KB newsletter. |
| 2026-09-16 | Gmail preserves threading headers on draft APPEND; Proton does not | A root + reply appended to `[Gmail]/Drafts` came back with `In-Reply-To` **and** `References` intact and the `Message-ID` unchanged; `group_threads` rebuilt them as one thread of 2. Proton returns the same drafts with `In-Reply-To` absent and `References` rewritten to a `@protonmail.internalid` value. | **D-009 is Proton-specific, not universal.** Gmail reply drafts thread correctly; only Proton ones need the "this will not thread in your UI" warning. |
| 2026-09-16 | `imaplib` quotes SEARCH arguments no more than mailbox names | `M.uid('search', None, 'SUBJECT', 'm2c roundtrip probe')` fails with `BAD Could not parse command` — the spaces end the command, exactly as for `M.select('All Mail')`. | Quote every multi-word value reaching `imaplib`, not just folder names: `f'"{term}"'`. `build_search_criteria` feeds values straight through, so any caller searching a phrase must quote it. |
| 2026-09-16 | A full-body Gmail fetch is minutes, not seconds | 400 messages with `(FLAGS BODY.PEEK[])` over `imap.gmail.com` takes ~7 min; 900 takes ~15. The same fetch against local Bridge is seconds. | Background every Gmail scan and poll for the result; do not run two large Gmail fetches concurrently. `just check` audits Proton only for this reason — auditing Gmail is a deliberate, slow act. |
| 2026-09-16 | `getaddresses` discards everything when handed two empty strings | `getaddresses(['dj@ai4hu.org', '', ''])` returns `[('', '')]` — not the address. One trailing empty is tolerated, two are not (Python 3.10's CVE-2023-27043 hardening treats the joined value as malformed). Building the list as `[msg.get(h) or '' for h in ('To','Cc','Bcc')]` therefore breaks on **every message with no Cc and no Bcc** — the commonest shape there is. | Pass only headers that are actually set. Caught by the send-guard tests, where it failed closed (refusing a legitimate recipient); the same construction elsewhere could just as easily drop a recipient silently. `compose.list_participants` passes one header at a time, so it is unaffected. |
| 2026-09-16 | A broken reply only splits a thread if nothing later names it | Stripping `In-Reply-To`/`References` from a **middle** reply does not split the thread: every later reply still lists the orphan in its own `References`, and union-find heals the gap. Only orphaning the **last** message produces two threads. Written as a test expecting a split, it returned no problems — the checker was right and the assumption was wrong. | `04_learnings.md`'s "thread completeness is not provable" is narrower than it sounds: the tool survives a correspondent whose client drops headers **mid-thread** as long as the conversation continues. The real blind spot is the last message of a thread, or a correspondent whose client strips headers on every message. Phase 2's deliberate break must therefore strip the FINAL reply. |
| 2026-09-16 | Proton appends an internal id to `References` on every stored message | Every message stored by Proton carries exactly one extra `@protonmail.internalid` at the end of `References` — step 1 was sent with no `References` at all and came back with one. Gmail's stored copies carry exactly the chain that was sent, nothing added. | Never assert `References` **equals** what was sent; assert it **contains** the expected ancestors. The extra id is unique per message and matches no `Message-ID`, so union-find just hangs a singleton off it — harmless for grouping, fatal for an equality assertion. |
| 2026-09-16 | Both providers keep a client-supplied `Message-ID` on SMTP submission | Every one of the 7 sent messages arrived at the other provider with the exact `make_msgid()` value generated on this machine (`@feynman`), through Proton Bridge **and** through `smtp.gmail.com`. Gmail only mints one when the header is absent. | A ledger of what was sent is valid for sent mail — but not for drafts, where Proton rewrites `Message-ID` on APPEND (D-009). The round-trip still reads each id back from the recipient's copy rather than trusting the sent value, because that asymmetry is exactly the kind of thing that changes without notice. |
| 2026-09-16 | A thread the tool splits can still read as one conversation to a human | The deliberate break arrived with subject `Re: m2c roundtrip 91fcac` and no threading headers. The tool correctly reports 6 + 1; the subject line alone gives no hint that anything is detached. | When reporting a thread, say "the tool grouped N messages", never "the thread has N". A message the owner can see in their client may be missing from what the agent reads, and the subject will not reveal it. Whether the Proton and Gmail UIs group it anyway is a Phase 5 screenshot question, not something to assume. |
| 2026-09-16 | markdown-it's `commonmark` preset has no tables | `render_markdown` carried `table`/`th`/`td` styles that nothing could ever reach: the preset disables the GFM table rule, so a pipe table went out as a paragraph of literal pipes with `<br>`s. Every draft to date happened not to contain one. | `.enable('table')` on the parser. A style entry proves nothing about the parser; the Phase 3 feature-coverage test (`content_body` must render every tag in `_STYLES`) is what caught it, before any live mail. |
